## 2. 归因：补桥为什么没提高触达

### 2.1 桥本来就不在「能不能开起来」这一层

接头卡是**线走完之后**才发的承接卡（`packages/adventure/cultivation.js` 里
「线真的走完那一刻」才把它排进队列）。它**不改这条线自己开不起来的条件**：
路径、岁数、境界、机会窗口（`packages/adventure/scheduler.js` 的长线档）。
⇒ **补桥对长线自身触达的影响，结构上就是 0。**

交接文档 §3.4 的那句预期（「有桥 140.3 次 vs 无桥 48.9 次 ⇒ 修桥是救低触达线的主要手段」）
**把相关性当成了因果**：当时有桥的那 9 条，恰好也是路径占比高、窗口宽的那几条。

### 2.2 阶段 3 真正动的是**路径分布**（背景故事线表）

同一批 200 条命，两棵树的路径分布（曾走过）：

| 路径 | 修桥前 `0e785b7` | 修桥后 `48f2963` | 差 |
| --- | ---: | ---: | ---: |
| 正教 | 74 | 58 | −16 |
| 散修 | 78 | 70 | −8 |
| **妖身** | **8** | **25** | **+17** |
| **幽灯** | 40 | 45 | +5 |
| **凡人** | 31 | 47 | +16 |

⇒ **妖身线暴涨的 17 条命，是背景故事线表（阶段 3.1）把 12 条背景里的「老猿教你控制妖身」派给了它们**，
不是桥给的。**正教/散修线的下滑也是同一件事**（背景表把一部分命派去了妖身与凡人）。

⇒ **⇒ 阶段 4 的方法论结论：跨阶段的「修桥前/修桥后」对照，只要中间还改了别的东西（这里是背景表），就是混淆的。**
本表之所以还留着修桥前那一列，是因为它本身就是证据。

### 2.3 「队列被占 / 优先级不对」—— **实测推翻**

交接文档猜低触达是「条件写错 / 队列被占 / 优先级不对」。逐条查完：

| 猜想 | 实测结果 |
| --- | --- |
| 条件写错 | **否**。16 条线「有机会」与「发出」**逐条相等**（28/28、41/41、10/10……），缺口全为 0。 |
| 队列被占 | **否**。「抽中了机会却没发出来」在 16 条线上**全是 0**。 |
| 优先级不对 | **否**。把长线表按「窗口先到期先开」重排（实验树实测）：`sect_feud` +1、`sect_trial` −1，**净收益 0**。⇒ 没动。 |

### 2.4 触达的真实公式

```
触达次数 ≈ 「窗口内还在那条路上」的命数 × 62%
```

- **62%** = 机会抽签一次命中（`content/cultivation-daily.js` 的 `storyOpportunity`，机会只抽一次）。
- 「窗口内还在那条路上」是最大的那一项：命会**换路**（离开宗门 → 散修、幽灯 → 散修），
  换了路以后那条线就不归它了 —— 这是**设计**（换路本身是玩家做的决定），不是缺陷。
  实测：45 条幽灯命里有 19 条中途转成散修 ⇒ `dark_method` 的「够格」只有 24 条。

## 3. 本阶段修掉的两个真缺陷

| # | 缺陷 | 症状 | 修法 |
| --- | --- | --- | --- |
| **A** | **急讯打断行动 ⇒ 存档校验崩游戏** | 行动进行中收到「家中有人打听包裹」的急讯时，被打断的行动若不在校验白名单里 ⇒ `validateProgression` 报「急讯暂停的行动」⇒ **整局抛错（白屏）**。实测：`echo_relic` 行动（打断时打的是「旧线索核查」） | `packages/adventure/progression.js`：把**事件前缀白名单**换成**结构校验**（快照得像个合法行动：有起止月、有结算、事件名非空）。⚠ 白名单是「人写的清单」，而打断对任何行动都成立 ⇒ 两处口径不一致才是病根 |
| **B** | **接头卡被「清链条阶段卡」的队列过滤误删** | 接头卡 id 是 `<线名>_joint_settled/_pending/_hidden` ⇒ **它以线名开头** ⇒ 凡是用 `startsWith(线名+'_')` 清队列的地方都把它一起清了。实测：`dark_sacrifice` 走完 24 次，接头卡只发 **1** 次（幽灯的命走完这条线多半紧接着换路 ⇒ `setPath` 把队列里的接头卡一起清了） | `packages/adventure/cultivation.js`：新增 `isChainStage(event)`（**阶段卡与接头卡分开**），5 处队列过滤统一改用它。修后接头卡 **311 → 330**，`dark_sacrifice` **1 → 20** |

⇒ 缺陷 B 修完后，**长线自身触达不变**（374）—— 这正是 §2.1 的直接验证：桥在「线走完之后」那一层。

## 4. 零触达卡台账（115 张 / 11 族）

### 4.1 ⚠ 先修一个**量法**的错：零触达有两种完全不同的原因

① **走不进去**（条件写错 / 队列被占 / 优先级不对）⇒ **缺陷**；
② **这条偏好没选过**（卡在那儿，只是我们用的那套固定偏好没走到）⇒ **不是缺陷**。

以前只看一种偏好 ⇒ 量出来的「零触达」大半是 ②。
**固定偏好下 132 张「零触达」**（修掉本阶段两处缺陷之前是 134 张）；换成**固定偏好 ∪ 随机探索**（400 条命）之后，
**真正的零触达是 115 张**，而这 115 张里：

| 族 | 张数 | 为什么到不了 |
| --- | ---: | --- |
| 凡人线停用 `m11_*` | 45 | 阶段 3.3 决定「凡人线只走五张」⇒ 其余停用不删（放回来只改 `content/mundane-kept.js` 一处） |
| 备主药矩阵空格 | 19 | `advance_material_<境>_<第几次>_<第几份>` 是三维矩阵，现实里走不到的那些格子 |
| 包裹备用编号 | 14 | `parcel_missing_1..7` / `parcel_exposed_1..7` 是「同一起事故再来一次」的备用编号 |
| 规则十二备用编号 | 11 | `r12_home_resolve_2..5` / `r12_home_leave_2..5` 是同一张卡的第 3–6 份拷贝 |
| 旧线索兜底 | 6 | `echo_<kind>_check_resume` / `_visit_resume` 是兜底编号，实走 `echo_resume_after_war` |
| 其它 | 7 | `early_demonic` / `early_beast` / `early_loose` / `beast_invitation` / `beast_acceptance` / `departure_terms` / `dark_oath_return` —— 各有各的前置 |
| 宗门评议后段 | 4 | `selection_3/4` 及其 `_result`：要先当上掌事 |
| 突破卡变体 | 4 | `breakthrough_<境>_3`：多数人前两次就过去了（交接文档已登记为已知） |
| 人脉网络支线 | 2 | `network_bottleneck` / `network_volume`：要特定心法与特定进度 |
| 接头卡收尾档 | 2 | `_joint_pending` / `_joint_hidden`：对应线第 0 步选「留退路」/「自己拿」就是**主动退出这条线** ⇒ 线没走完 ⇒ 不发接头卡 |
| 宗门复仇线 | 1 | `sect_revenge`：要先经历宗门崩散（`sect.phase` 变 `camp`） |

⇒ **结论：没有一条是「写坏了走不进去」。** 台账落在 `tests/fixtures/reach-gaps.json`，
由 `scripts/audit-reach.mjs` 盯着：**新出现的零触达 ⇒ 报红**；**台账里的卡被走到 ⇒ 也报红**（该更新台账）。

⚠ **台账与样本量绑定**（200 条命 × 2 策略 = 400 条）：「零触达」本来就是样本量的函数
（一条少见的卡，样本小的时候可能压根没撞上）⇒ 换样本量必须重写台账。

⚠ **2026-11-08 · 阶段 2 更新（重心加成，§1.12）**：上面这张表是**阶段 4 当时的快照**，
台账（`tests/fixtures/reach-gaps.json`）已经变了：
  · **「接头卡收尾档」整族删掉了** —— 重心加成让技艺练得更稳，
    `dark_pursuit` / `loose_portal` 两条线现在**能走完** ⇒ 那两张接头卡真发出来了
    （实测 `序列基线-6` 原本 54 岁战死，现在活到 276 岁）。
  · `r12_direction_3` 加进「规则十二备用编号」（原来只有 `_4` / `_5`）。
⇒ **门禁以台账文件为准**（`scripts/audit-reach.mjs` 只读 `tests/fixtures/reach-gaps.json`），
这张表是历史证据，不是当前状态。

### 4.2 接头卡的 `_pending` / `_hidden` 为什么少

不是「发不出来」，是**选了就退出**：那三条线第 0 步的「留退路」选项挂着 `stopChain`
（`content/story-rules10.js`：选它＝「你留在谷口照看补给，没有深入兽群所在的山谷」）
⇒ 线没走完 ⇒ 不发接头卡 ⇒ 也就没有 `_joint_pending` 这一档。
