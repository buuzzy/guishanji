# 归山记网页端与微信小程序端独立仓库迁移方案

编写日期：2026-11-06  
用途：供两台电脑上的开发者执行迁移、验收和发布切换。  
状态：方案与代码依赖核查已完成；尚未创建新仓库、迁移代码、删除入口或发布新小程序。

## 1. 目标与最终归属

把归山记从 1in8b 的附加玩法迁为独立产品，保留已经完成的剧情、修行规则、网页与小程序体验。

| 仓库 | 迁移后的职责 |
| --- | --- |
| 新归山记仓库，暂以 `buuzzy/guishanji` 表示 | 归山记共享剧情与引擎、网页端、小程序端、素材、构建、测试及产品文档 |
| `buuzzy/1in8b` | 只维护 1in8b 网页端及微信小程序端；迁移切换结束后移除归山记运行代码和入口 |
| `buuzzy/xianxia-life` | 保留历史、来源及旧版本追溯；新仓库验收、交付并稳定后停止新增开发，最后再设为归档 |

`guishanji` 是建议名称，不代表仓库已经创建。正式仓库名、公开或私有、新域名和新小程序 AppID 在实施前填写。

两个端共用一份当前剧情与规则源码，分别维护网页和微信界面。新仓库不继续通过另一仓库的 PR 或手动复制来获取当前剧情。为了兼容旧存档保留的冻结版本属于明确的历史依赖，不是另一份可任意修改的当前规则。

本轮迁移不增加新剧情、不调整修行数值、不重做画风。先证明迁移前后行为一致，再单独开展下一版迭代。

### 2.3 不能只搬一个文件夹

已读回的小程序实施文档和代码揭示了这些依赖：

1. 全局 `miniprogram/app.wxss` 中包含顶栏、年龄盒、倍速、面板、弹层及字体变量。仅复制分包会缺少这些样式。
2. 归山记页面还导入自己分包内的 `styles/official-*.wxss`；现有样式测试对照的是 1in8b 官方页面，迁移后必须有独立、可追溯的对照样式。
3. `pages/life/life.js` 和 `pages/past/past.js` 的返回失败兜底会跳到 `/subpkg/engine/pages/index/index`。新产品不能保留这个地址。
4. 现有 `app.js` 包含 1in8b 引擎加载、官方存档退役清洗、音乐与就绪逻辑。新产品需要最小启动层，不能整份照搬并继续加载官方游戏。
5. `scripts/build-xianxia-mp.mjs` 依赖 `scripts/lib/xianxia-bundle.mjs`、构建工具和来源锁；不能只搬生成的 `runtime/engine.js`。
6. 当前网页构建会同时输出旧 `apps/web` 和当前 `apps/preview`，且根首页指向旧 Web。新产品应明确把当前归山记试玩转为正式网页入口。
7. 现有存档层与往期人生页没有完成导出、导入功能。不能把存档跨 AppID 迁移写成现成能力。

## 3. 目标仓库结构

第一阶段优先保留现有目录名与相对导入，减少搬迁引入的错误。`apps/preview` 可以先作为正式归山记网页的源码目录，目录重命名放到之后。

```text
guishanji/
├── apps/
│   └── preview/                   # 当前归山记网页、样式、Canvas、组件
├── content/                       # 当前剧情、地域、功法及历史冻结表
├── packages/
│   ├── adventure/                 # 共享状态、规则、推进与存档校验
│   └── ...                        # 由实际依赖图决定保留的公共模块
├── miniprogram/
│   ├── app.js                     # 新产品最小启动层
│   ├── app.json                   # 独立页面/分包注册与产品标题
│   ├── app.wxss                   # 迁入并核验的归山记全局样式
│   ├── pages/home/                # 独立首页与必要的加载/失败重试界面
│   ├── pages/legal/               # 对应归山记的说明与隐私页面
│   ├── subpkg/xianxia/            # 先保留现有游戏页面、桥接与组件路径
│   └── sitemap.json
├── reference/                     # 视觉来源、样式快照与哈希锁，不作远程依赖
├── scripts/                       # 网页/小程序构建、依赖审查、各端验收
├── tests/                         # 同源、旧档、迁移协议、浏览器与适配测试
├── docs/                          # 迁移台账、发行说明、操作手册
├── project.config.json            # 新小程序项目配置
├── package.json
└── package-lock.json
```

这是目标结构，`pages/home`、`pages/legal`、`reference` 及独立启动文件均为待新增。它们不能被标记为已经实现。

### 3.1 当前规则只有一个编辑来源

- `packages/adventure/`、`content/` 是当前规则的唯一编辑来源。
- 小程序运行时由这份源码构建，不在生成文件里修剧情。
- 初次迁移可暂时携带 `vendor/xianxia-r12` 和画面快照，先证明旧产物可复现；迁移稳定后改为从新仓库的同源文件构建。
- 切换构建来源后，旧来源锁作为历史证据保存；新的构建清单记录新仓库的源码标识、输入文件哈希及输出哈希。不要伪造旧上游提交和新来源的关系。
- 冻结规则8及网页已有旧规则仍各自校验。未证明某历史模块不再被任何支持版本使用前，不删除它。
- 不建立对 1in8b 或 xianxia-life 的运行时网络依赖、Git 子模块依赖或相邻本地目录依赖。

### 3.2 避免把无关旧产品带入新产品

`xianxia-life` 历史上还包含旧版 Web 游戏。新仓库面向当前归山记，不把两个历史首页继续作为两个产品发布。

先列出当前网页、共享引擎、旧档兼容的完整导入图，再移除仅供旧 `apps/web` 使用的页面与模块。不能按文件名或版本号猜测哪些文件可以删。测试也应分为当前产品必须通过的测试与保留历史记录，不能直接删测试来获得“全绿”。

- 六个 `scripts/test-xianxia-*.mjs`：build、mp、storage、style、art、equivalence；根据完整依赖图携带它们使用的测试辅助文件。

`runtime/engine.js` 是构建产物。初始迁入用于校验，不把它作为未来唯一可维护的规则代码。

### 4.3 新增或调整

- 独立 `App`、首页、页面注册、应用标题、错误恢复和加载流程。
- 新 AppID 对应的项目配置、产品说明、隐私声明与必要域名配置。
- 页面返回、导航失败、分享路径等路由；移除回到官方 1in8b 页面的兜底。
- 新产品的网页根入口、构建与部署配置。
- 独立样式对照源及 provenance/哈希锁。
- 存档导出/导入协议与用户操作界面。
- 新仓库的开发约定，替换原来限定“只做 HTML”“另机接入”等已经不适用的历史指令。

根目录 ESM 与小程序 CommonJS 的执行方式也要核查：网页项目现在有 `type: module`，小程序桥接文件使用 `require/module.exports`。保持微信源码工作方式，调整 Node 测试加载边界；不能为了让测试加载而整体转换小程序模块，再引入额外编译差异。

## 5. 实施阶段与阶段验收

### 阶段0：锁定来源和保护工作区

1. 重新读取两仓库当前 HEAD、PR 状态、源码树和小程序快照锁。
2. 检查 macOS 与本机工作区状态。有未提交工作时先由执行者保存或提交，不能覆盖。
3. 1in8b 的旧 Web 工作分支保留；切到已同步的 main 或明确的迁移分支，不能把旧分支误当最新来源。
4. 为实际来源提交创建迁移前标签/备份引用，记录源 SHA；不强制推送、不重写原分支。
5. 确定新仓库名称、可见性、负责执行微信验收的人；新 AppID 可以后补，但正式微信验收与上传必须使用正确账号及 AppID。

**通过标准：** 来源记录完整、工作区无未保护改动、小程序锁的输入与 xianxia-life 选定基线逐文件一致。不一致则先列明差异并确定保留哪部分，不能随意选“较新的文件”。

### 阶段1：创建新仓库并迁入共享源码

1. 以 xianxia-life 已验证的归山记分支作为基础创建新产品仓库，保存源历史或建立可追溯的导入记录。
2. 新仓库建立 `main` 和迁移工作分支，例如 `migration/standalone`。
3. 迁入当前网页、共享引擎、剧情、历史兼容和必要测试。
4. 导入 1in8b 中的归山记适配代码，记录来源提交与路径映射。
5. 合并两个 `package.json` 的实际依赖和脚本，生成新锁文件；不保留 PostgreSQL、官方游戏部署等与归山记无关的工具。

**通过标准：** 原始导入文件能与来源哈希核对；共享规则的单位测试和受控旧档继续执行基线通过。此时不要求新网页首页或独立 App 已完工。

### 阶段2：完成独立网页

1. 当前归山记成为网页根路径首页，保留旧 `/preview/` 路径的重定向或兼容入口。
2. 去掉面向开发者的“HTML试玩”等产品提示，保持已确认的页面与交互，不借迁移重做 UI。
3. 更新服务脚本、静态构建和站点清单，使它们发布当前归山记页面，明确处理旧 `apps/web`。
4. 本地完成完整人生、存档刷新恢复、自动抉择、移动视口与静态构建验收。
5. 先部署预览环境，再准备正式域名切换；不改 1in8b 网页域名、部署目标和官方静态快照。

**通过标准：** 从新项目根目录独立构建、访问即可玩，不依赖相邻仓库；源码和静态版读取同一规则及素材；现有选择、时间与旧档行为保持一致。

### 阶段3：完成独立小程序启动与界面

1. 最小主包提供首页、启动/重试、必要的产品说明，不加载 1in8b 引擎或官方就绪屏障。
2. 主包注册归山记分包。先保留 `subpkg/xianxia` 和三页路径，避免同步改动全部测试与导航。
3. 从独立首页进入命盘或继续人生；缺少有效存档时回到新产品首页/命盘，不回到 `/subpkg/engine`。
4. 迁入全局布局与字体样式；日夜主题、胶囊避让、弹层、滚动、地图和雷达与既有归山记对照。
5. 使用新的项目配置和 AppID；原 1in8b AppID 只保留在历史来源记录，不作为新项目默认值。

**通过标准：** 新产品从冷启动、后台返回、页面返回和失败重试均能进入正确流程；不存在对 1in8b app/globalData/页面地址的运行依赖。

### 阶段4：同源构建与包体验收

1. 初次先证明迁入快照可复现原规则12运行时，保留现有 Babel 降级、语义校验和压缩处理。
2. 构建来源改为新仓库共享源码与画面输入；建立源码输入哈希、规则版本、生成物哈希和工具版本清单。
3. 用相同种子、选择序列和推进月份，对比网页引擎、小程序运行时和状态变化；不能只比较最终境界。
4. macOS 运行微信开发者工具真实编译，测量主包、每个分包及总包体。测量必须发生在独立 App 配置和迁移后布局上。

**已知基线：** 1in8b 现有实施文档记录归山记分包编译后 `1,985,967` 字节，相对当时使用的 `2,097,152` 字节上限余 `111,185` 字节（约5.3%）。这是另一台电脑、原项目布局的历史实测，不是本机或新产品的验收结果。

不把整个游戏直接搬到主包。不把 `1,738,614` 字节的仓库运行时文件大小当成微信编译体积。历史记录也显示 terser 预压缩降低了仓库字节，未降低该次 IDE 编译体积。

若新包超限或无法容纳启动层/存档迁移功能，按实际测量再选择：

- **方案A：规则运行时独立普通分包。** 游戏页面分包异步加载运行时，完成后注入 session/view-model/art；加载失败可重试，不能在模块顶层继续同步读取未加载引擎。需专项核查微信分包依赖规则与循环依赖。
- **方案B：构建兼容版本子集。** 小程序入口明确支持规则8和12；只有依赖审查与旧档等价验收证明安全后才裁剪其他执行器。网页支持的旧版本继续保留。不能简单按文件后缀删历史表。

迁移阶段以保持行为为先，裁剪或异步加载作为单独、可回退的提交。没有测量证据时不承诺能节省多少字节。官方规则实施时核对 [微信小程序开发文档](https://developers.weixin.qq.com/miniprogram/dev/framework/)，特别是分包、异步加载、存储和上传限制。

**通过标准：** 同源状态对比、旧档和语义门禁通过；新配置真实编译和上传预检通过，包体台账注明测量环境、工具版本及可用余量。

### 阶段5：完成玩家存档迁移

按第6节实现旧入口导出、新产品导入。新小程序发布前先让旧版本具备导出能力；迁移协议相同，UI可以分别适配。

**通过标准：** 从原 1in8b AppID 实际导出一个规则8和一个规则12归山记存档，在新 AppID 下导入后继续；断电/中断、损坏、超额和重复导入不破坏原有存档，官方 1in8b 存档逐字不变。

### 阶段6：新产品发布并观察

1. 新网页预览部署验收，再切正式地址。
2. 新小程序完成独立注册、后台配置、提审和发布；备案、类目、名称及隐私声明按新产品实际情况处理，原 AppID 的审核结果不能直接视作新 AppID 已通过。
3. 旧归山记入口增加迁移说明和存档导出引导，明确新产品名称及查找方法。
4. 若使用跨小程序跳转，填入已确认的新 AppID，并验证实际跳转条件和失败提示；新 AppID 未准备好时不设置失效按钮。
5. 观察新产品冷启动、存档保存、旧档继续、早逝/突破、跨大陆及长行动的实际体验。

**通过标准：** 两端可正常访问，真实玩家迁移路径可用，严重阻断问题已经处理；保留这一阶段的版本号和验收记录。

### 阶段7：清理 1in8b 并结束旧仓库开发

先完成第7节的分阶段清理与回归，再移除最后的迁移过渡入口；最后处理 xianxia-life PR #2 和归档。

**通过标准：** 1in8b 正常提供自己的网页与小程序产品，新仓库成为归山记唯一开发源，发布与存档不存在对旧游戏入口的依赖。

## 6. 存档迁移设计

### 6.1 为什么必须单独实现

微信本地缓存按小程序身份隔离。即使新产品保留 `xianxia.v1.*` 相同键名，也不能直接读取原 1in8b AppID 下的缓存。

现有归山记存档层有分片、双 manifest 槽与写后校验，但公开接口是保存、读取、列出、删除等，尚无用户导出/导入流程；实施文档也将跨端导入明确列为未实现。本方案不假设已有玩家账户或云端同步。

### 6.2 首选传输方式

优先使用用户可保存和传送的 JSON 存档文件：旧小程序选定一段或多段归山记人生，生成迁移文件；新小程序选择文件并核验后导入。

具体微信文件保存、转发和选取能力先在开发者工具与手机验证，再确定最终 API 和操作说明。若文件通道不满足实际设备条件，另设计文本传输，但大存档不直接塞成二维码或要求用户手工拼接几十段文字。二维码可承载迁移说明，不能凭空承载完整大存档。

不新增服务器、中转账号或自动云同步作为默认前提。文件由玩家自行传送，不由助手发送玩家数据。

### 6.3 迁移封套

封套应明确包含：

| 字段 | 用途 |
| --- | --- |
| `format`、`formatVersion` | 区别归山记迁移文件与官方人生、普通 JSON |
| `sourceProduct`、`sourceBuild` | 标识来源产品和构建版本；不携带凭据 |
| `createdAt` | 说明导出时间 |
| `activeId`、所选人生列表 | 指出继续哪段人生 |
| 每段完整状态、规则版本与字节数 | 保留年月、随机流、出生、人物、库存、待选项和长行动 |
| 内容校验摘要 | 检查截断或传输损坏；普通摘要不等于防篡改认证 |

导出从现有 `readLife` 读取已经验证的状态，不直接打包未核验的存储键。不能混入 `one8b.*`、`o8b.*` 或别的玩法存档。

### 6.4 导入及失败处理

1. 在写入前核验格式、文件大小、字段、支持规则和完整状态。
2. 规则8保持8，规则12保持12；不重新生成种子、命盘、寿元、随机数或往事。
3. 重复 ID 比较内容：完全相同可提示已存在；不同内容让用户选择另存，不能静默覆盖。
4. 确认用户选择和容量后，通过原分片/双槽写入协议逐段保存并读回校验；最后明确列出成功、未导入和失败的人生。
5. 多人生文件若部分导入，界面必须说明，不假称整包成功；尚未验证的新 manifest 不能取代可读的旧 manifest。
6. 模拟截断、格式错误、不支持规则、额度不足、写入异常和应用中断，验证旧档仍可继续。
7. 导出后不自动删除原 AppID 的数据，导入后也不要求玩家立即卸载旧小程序。

### 6.5 网页旧档

- 若保留原网页域名及存储来源，尽量维持网页存档键和协议。
- 更换域名、协议或端口可能改变浏览器存储来源，不能承诺旧存档自动出现在新站点。
- 如需迁移现有网页玩家，先在原归山记网页提供导出，再在新网页提供导入；跨平台迁移另列兼容范围。
- HTML 存档和微信分片档的存储协议不同。共享的是合法人生状态，不是直接复制 localStorage 到 `wx` 缓存。

## 7. 1in8b 的清理范围和下线顺序

### 7.1 代码入口与依赖

确定需要审查/移除的现有位置：

- `miniprogram/subpkg/engine/pages/index/index.wxml` 中“归山记 · 修仙人生（实验）”按钮。
- 对应 `index.js` 中 `goXianxia` 跳转方法。
- `miniprogram/app.json` 中 `subpkg/xianxia` 的分包注册。
- `miniprogram/subpkg/xianxia/`。
- `vendor/xianxia-r12/`、`vendor/xianxia-r12-art/`，以及依赖审查确认仍存在的旧归山记快照。
- 专用构建脚本、六道测试、回归注册、包体测量目标、CI步骤及相关依赖。
- 当前产品文档中仍指向旧实验入口的说明。

不能只删除分包后留下按钮、路由或 `require`，也不能因为复制过样式就删除 1in8b 自己的 `app.wxss`、官方样式或通用构建模块。

依赖包按实际引用清理：例如构建工具可能也服务官方引擎，不因归山记迁出就直接卸载。官方静态快照、来源声明、用户存档、部署环境和 1in8b 自己的包结构保持有效。

建议在完整源码范围执行引用搜索，而非只搜中文产品名：

```sh
rg -n 'xianxia|guishan|goXianxia|subpkg/xianxia' miniprogram scripts docs .github package.json
```

结果应逐条区分运行引用与历史说明；历史记录允许保留，但要标注入口已迁出。

### 7.2 三步下线，避免玩家失去导出机会

1. **过渡版：** 保留原归山记玩法，增加新产品说明和存档导出，等待新产品正式可用。
2. **迁移版：** 新产品上线后，提供导出/前往新产品入口。需要继续提供导出时，保留读取旧存档所需的兼容能力；不能把它连同游戏分包一起提前删掉。
3. **最终纯 1in8b 版：** 完成事先公布的迁移窗口后，移除最后过渡入口及归山记专用代码。迁移窗口由运营确认，不在文档里擅自确定天数。

这份方案把第2步视为暂时的迁移工具，不是继续在 1in8b 开发第二款游戏。最终状态符合“只做 1in8b”。

不主动清除手机上遗留的 `xianxia.v1.*`。若有明确需要释放缓存，必须作为用户可理解、可选择的独立操作，先确认已导出或不再需要；不能混入官方存档清洗。

### 7.3 清理后的验收

- 官网和小程序中没有失效归山记游戏入口。
- 1in8b 出生、人生、自动抉择、往期人生、主题、存档恢复及法律页正常。
- 官方内容、Web锁定快照与产物检查通过，原部署目标未被新产品替换。
- 小程序分包列表、加载、编译及上传预检通过；测量清理后的真实包体。
- 官方 `one8b.*` / `o8b.*` 存档在删除、启动及退役清洗流程中保持原有保护。
- 新产品源码与资源不再从 1in8b 当前目录读取。

## 9. 两台电脑的协作方式

### 这台 Windows 电脑

- 核对 GitHub 源码、依赖、迁移清单和同源状态。
- 完成可在 Node/浏览器执行的构建、等价性、存档协议和网页测试。
- 创建或更新迁移 PR、记录来源与校验结果。
- 通过本机会话允许的 GitHub MCP/其他已验证通道同步；不把凭据写入仓库或文档。

### macOS 电脑

- 在已安装微信开发者工具的环境同步迁移分支。
- 完成独立App配置、真编译、包体、预览/体验版和手机实测。
- 完成新小程序注册配置及用户需要本人执行的审核/发布操作。
- 把实际测试结果写回同一个新仓库，并以PR形式完成1in8b入口下线。

迁移只需为新产品建立一次独立目录。之后两台电脑都在各自已有新仓库目录中 `fetch/pull` 对应分支，不每次重新 clone、不默认拆成大量 ZIP 传输。

1. 保留 xianxia-life 的原始归山记开发历史；可在新的空仓库导入选定分支的历史，然后新增小程序适配导入提交。

3. 如执行者选择只导入快照，必须明确新仓库历史从导入开始，并保留两份来源记录；不能声称保留了全部原提交。
4. 不在原两个仓库执行强制推送、历史过滤或批量删分支来完成迁移。
5. 新仓库的迁移PR、1in8b的过渡/清理PR分别交付，分别验收；不要把源码迁入成功等同于旧入口已经可下线。

7. 新产品稳定后再归档 xianxia-life，README说明新位置；旧提交、标签和来源证据仍保留可读。

每次发布读回核验远端目标分支：不能仅因上传请求成功就判定本地与线上一致。MCP文件提交可能产生与本地不同的提交SHA，应分别记录本地/远端SHA，并核对完整文件、模式、blob和子树。不要把两个SHA不同直接误判为内容不同。

## 11. 发布切换与回退

| 阶段/故障 | 回退方式 |
| --- | --- |
| 新仓库导入或等价测试失败 | 保持原两个仓库和现有产品，回到迁移前提交；不下线入口 |
| 独立网页失败 | 预览环境停止切换，或将新网页回到已验证构建；不触碰1in8b网页 |
| 新小程序加载、包体或存档失败 | 保留旧入口及旧存档，修复新体验版；使用微信平台当时允许的撤回/重新发布流程，不假设可以任意回滚正式版本 |
| 玩家导入失败 | 保留迁移文件和原AppID存档，保留新AppID之前的可读manifest，提供明确重试信息 |
| 1in8b清理发生回归 | 还原清理PR并重新构建/发布需要的版本；不要重置玩家本地数据 |
| 两台电脑出现分叉 | 先检查差异、合并或另开修复PR，不用force覆盖另一台的工作 |

回退目标是恢复可用产品与可读存档，不是删除新仓库、清空所有缓存或强制把旧人生升级。

## 12. 风险与处理结论

| 具体问题 | 本方案的处理 |
| --- | --- |
| 搬分包后界面变形 | 迁入全局样式与字体，保存独立视觉对照，比较实际页面与Canvas |
| 返回按钮跳到不存在的1in8b首页 | 全部导航、失败兜底和分享路径改为新产品路径，覆盖冷启动和返回失败 |
| 新AppID读不到旧档 | 先实现旧导出/新导入，再下线原入口；不假设账号/云同步 |
| 编译超限 | 保留分包，按新布局真实测量，必要时单独做异步运行时或版本子集构建 |
| 两端剧情分叉 | 当前共享源码唯一可编辑，生成物与历史版本分别锁定 |
| “瘦身”破坏规则8旧档 | 支持版本明确登记，裁剪前后继续执行状态逐值比较 |
| 原Web首页混进新产品 | 构建入口明确改为当前归山记，旧Web依赖经图审查后处理 |
| 误删1in8b通用样式/工具 | 清理前做全项目引用审查，按专用与共享依赖分别处理 |
| 把历史记录当本轮验收 | 原台账保留来源，新仓库与新AppID重新记录真实结果 |
