## 0.6 第三轮：真机反馈的七个问题（2026-11-03 晚）

第二版做完、用户上真机后指出七个问题。逐条查证后发现**五个是真 bug、两个是口径错**，
根因与修法如下（全部由 `xianxiastyle` / `xianxiamp` 钉死）。

### 参照系怎么分（这一轮最关键的一条）

| | 照谁 |
|---|---|
| **视觉 / 版式 / 组件排序** | 官方 1in8b 小程序（`subpkg/engine/pages/{roll,life,past}` + `styles/`） |
| **内容 / 文案 / 数值口径** | 上游修仙网页端（`xianxia-life/apps/preview/app.js` + `life-panels.js`） |

⇒ 壳抄 1in8b，内容抄修仙网页端。**两套参照物都说得通，但说的不是同一件事。**

### 七个问题的根因与修法

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 一出生就 16 岁 | `birth.startAge` 真值是 **0**（上游 `birth.js:19` 写死 `startAge: 0`），我们用 `\|\| 16` 取 ⇒ **0 是假值**被当成「没有值」。上游 `engine.js:493` 的校验是 `![0,16].includes(...)` ⇒ **0 和 16 都合法** | 全部改 `?? 16`（`page-model.js` / `view-model.js`） |
| 2 | 部分组件字体偏大 | ① 官方 `life.wxss` 的字号写的是**标签选择器** `button b` / `button .wx-small`，而小程序 WXML 没有 `<b>`（`check.mjs` 明令禁止 HTML 标签）⇒ **`button b` 匹配不上 `<text class="b">`**；`.s` 在 `.ch` 里**完全没有规则** ⇒ 选项两行都落到父级 `button` 的 30rpx。② 我们自加的 `.sheet-note` 写 12.5px（网页端是 11px）、`.realm-steps .step` 写 24rpx | 副行改用官方**已有的** `.wx-small`（25rpx = 12.5px）；页面 wxss 补 `.dec .ch button .b { font-weight:600; font-size:30rpx }`（30rpx = 15px，与官方 HTML 端 15px 一致）；`.sheet-note` 改 11px；`.realm-steps .step` 改 13.5px |
| 3 | 弹层「关闭」按钮被右上角悬浮按钮盖住，点不到 | `sheetPadTop` 只用了 `statusBarHeight`，**少了 44px** ⇒ 弹层的 `.hd` 行顶到了胶囊那一行。官方 `app.js:165-167` 是 `safeArea.sheetPadTop()`（胶囊底边 + 8px，兜底状态栏 + 44） | 修仙分包自写 `bridge/safe-area.js`（**不引用**官方主包的 `ui/safe-area.js`，守隔离口径），三页的 `sheetPadTop` 都改用它；顶栏右侧也按胶囊位置让位 |
| 4 | 人生地图文字格式乱（`NaN`） | **WXML 的 `{{}}` 不支持字符串拼接**（`+` 是算术）。原写法 `{{item.enabled ? '前往 · ' + item.fee + … : item.reason}}` | 整句在 JS 侧拼好（`places()` / `grounds()` 给出 `sub` 字段），WXML 只输出 `{{item.sub}}` |
| 5 | 轮盘转的是大陆，不是角色名 | 上游网页端转的是**角色名**：大字 `f.name`，小字 `f.place.name · f.address · f.household.name`；中间帧机制是 `birthFacts(seed + ':轮转:' + turn++)`。我们自造了一个 `engine.GEOGRAPHY` 的大陆列表 | 删掉自造列表，改用引擎已导出的 `birthFacts`（实测与 `createRun(seed)` **完全同源**）：`rollerFacts(seed, turn)` / `finalFacts(seed)`。节奏公式、26 帧、定格停 650ms 一个字不改 |
| 6 | 轮盘之后没出现角色名，人生页却有 | `cert` 字段**同时**承载「正文（字符串）」与「角色名（对象属性）」⇒ WXML 的 `{{cert.name}}` 对字符串取属性 ⇒ `undefined` | 拆成 `certName`（名字）与 `certText`（正文）两个字段 |
| 7 | 状态条显示「灵石/修行/心境」，灵石与下面重复 | 那三格是**自己编的**。上游网页端是 `[['体力',health],['心境',mind],['悟性',insight],['胆识',courage]]`（四格），官方 1in8b 是「健康/幸福/知识/关系」（四格）—— **两个参照物都不是灵石** | 改成网页端四格；条形图宽度在 JS 侧钳到 0–100（官方网页端是 `clamp(r,0,100)`）；灵石只留在「灵石与家产」面板 |

### 顺带按「检查全局」补的两项

| # | 现象 | 修法 |
|---|---|---|
| A | 决策卡抬头写死「抉择」 | 改「N岁 · 这一刻由你决定」（网页端口径，用户拍板） |

## 2. 规则「唯一来源」是怎么保证的

修仙规则**只有一份实现**：上游仓库 `buuzzy/xianxia-life`（分支 `feature/adventure-preview-v01`，
commit `c0baad36`）。本仓库不手抄第二套规则表，而是：

```
vendor/xianxia-r8/            ← 锁定快照（37 个源文件，逐个 SHA-256 记在 baseline.lock.json）
        │  node scripts/build-xianxia-mp.mjs
        ▼
miniprogram/subpkg/xianxia/runtime/engine.js   ← 生成物（981,328 字节）
        │
        └─► scripts/test-xianxia-equivalence.mjs
              12 个种子 / 7000 个月 / 200 个决策点
              源仓库（ESM）vs 产物（CommonJS）**逐值全等**
```

刷新快照（要求上游工作树干净）：

```sh
node scripts/build-xianxia-mp.mjs --refresh=../xianxia-life
```

校验产物是不是最新的（CI 跑的就是这条）：

```sh
node scripts/build-xianxia-mp.mjs --check
```

⚠ **不要直接依赖 `../xianxia-life` 那个目录**：
CI、Windows 那台机器、任何没克隆过上游的人都没有它 ⇒ 门禁会直接坏掉。
仓库里存的是**锁定快照**，任何机器都能构建、能对拍。

## 3. 打包器（为什么自己写）

仓库里没有 rollup / esbuild，也没有 `@babel/plugin-transform-modules-commonjs`
（只有 optional-chaining 与 nullish-coalescing 两个语法插件）⇒ 自己写了一个
`scripts/lib/xianxia-bundle.mjs`（acorn AST 改写 ESM → CJS）。

它做三件上游源码必须做的额外处理：

1. **ES2021 逻辑赋值**（`||=` / `&&=` / `??=`）：修仙闭包实测 **13 处** ⇒ 改写成 `a || (a = v)`。
   成员表达式左值用 IIFE 写回（避免重复求值对象/下标）。
2. **活绑定检查**：被导入的 `let` / `var` 若会被重新赋值 ⇒ **直接报错退出**（快照会失真）。
3. **语法降级**：`?.`（实测 434 处）与 `??`（14 处）降级到 ES2019
   （微信上传校验拒收 ES2020；这条在 `check-mp-syntax.mjs` 里也盯着）。

产物保证：**同样的输入 ⇒ 逐字节相同的输出**（清单里不写时间戳、不写绝对路径）。

## 5. 存档（`xianxia.v1.*`）

**没有照搬官方那套**（官方是单键整档，微信单键上限 1 MB ⇒ 迟早撞墙），
也没有照搬 HTML 端的 `AdventureStore`（那是浏览器，3 MiB 上限）。

本仓库的做法：**分片 + 双 manifest 槽 + 读回校验**。

写入顺序（不可换）：

1. 校验状态（引擎 `validateRun`）；
2. 写**新一代**的全部分片（目标 ≤ 512 KiB 一片）；
3. 逐片读回，核对字节数 + SHA-256；
4. 把 manifest 写到**另一个**槽（两个槽交替）；
5. 读回 manifest 核对；
6. 全过才算「已保存」。

失败时**保留旧 manifest 与旧代**（绝不先删旧档腾空间）。
清单读不出来 ⇒ **停止写入**（code `corrupt`），
否则会把「清单坏了」变成「人生索引丢了」，而旧分片还躺在盘上没人认领。

只保留当前代 + 上一代（可恢复备份）。

哈希用**纯 JS SHA-256**（`bridge/hash.js`），不依赖 `TextEncoder`
（`adapter/platform.js` 里的 `TextEncoder` 是**长度占位**，不能用来算字节数）⇒
UTF-8 字节长度自己算，与 Node 的 `crypto` 对拍 210 组样本一致。

## 6. 决策卡与自动抉择

决策卡文案与 HTML 端（`apps/preview/app.js` 的 `showDecision`）**逐字一致**：

- 抬头：`{年龄}岁 · 这一刻由你决定`
- 小字：`{地域} · {境界} · {灵石} 灵石`
- 不可选：`暂时无法这样做：{原因}`
- 底注：`未回应时，年月暂停。选好之后，日子继续往前走。`
- ⚠ **不显示成功率**（HTML 端也不给玩家看）

自动抉择：

- **默认关**；
- 只在「当前可选项」里挑，**不读**成功率、不读未来收益、不读死亡结果；
- 用**自己的**随机流（不动引擎的随机流 ⇒ 自动选择不改变人生本身的走向）；
- 手动抢先选 / 收起决策卡 / 页面隐藏 ⇒ 立刻作废这次计时；
- 等待时长 1200 ms（与官方人生页一致）。

## 14. 第六轮（2026-11-05）：空白页根因 —— for-of 的 `var` 作用域被微信转译切断

### 14.1 现象（用户真机报的）

> 「从主页（1in8b）的页面底部点击『归山记』，进入的页面是空白的，居中展示四个字『命盘转动』。」

用户明确要求：**只分析，禁止修改代码**。本节记录根因与修法。

### 14.2 根因链（每一步都有实证）

| 步 | 事实 | 怎么证的 |
|---|---|---|
| ① | 上游用了可选链 `s.journey?.cultivationTravel` | `vendor/xianxia-r8/packages/adventure/cultivation.js:295` |
| ② | 降级把它展开成**带临时变量**的写法，`var` 声明落在 **for-of 循环体**里，而循环**头部**（迭代表达式）已经在用它 | `miniprogram/subpkg/xianxia/runtime/engine.js`（降级产物） |
| ③ | Node 里 `var` 是函数级提升 ⇒ **一切正常** ⇒ 所有 Node 门禁都看不见 | 随机人生 300 次 + 50 个种子 `validateRun` 全过 |
| ④ | 微信开发者工具做 ES6→ES5 转译时，因为循环体里有**闭包引用了循环变量 `t`**，把循环体**抽成独立函数 `_loop3`** ⇒ `var` 跟着被关进那个函数，循环头部的赋值留在函数**外面** | 从 IDE 的编译缓存里抓到转译后产物（`WeappCompileCache`） |
| ⑤ | 头部引用到一个不存在的变量 ⇒ `ReferenceError: _s$journey11 is not defined` ⇒ 未捕获 ⇒ 出生页 `onLoad` 中断 ⇒ `rolling` 停在初始 `true`、`rollName`/`certName` 为空 ⇒ **只剩居中的「命盘转动」** | 用 `miniprogram-automator` 在 IDE 模拟器里复现，异常栈顶正是 `revised_validateCultivation → validateCultivation → validateRun` |

### 14.3 触发条件（实测出来的，比「看起来像」精确）

**关键**：不是「for-of 体内有 `var`」就炸，而是**同时**满足下面两条才炸：

1. 循环**头部**用到了那个 `var` 声明的变量；
2. 循环体里有**闭包引用了循环变量**（`t`）。

微信开发者工具 2.02.2608080 实测（`/tmp` 里的最小复现）：

| 写法 | 结果 |
|---|---|
| 体内有闭包引用 `t` + `var` 在体内 + 头部引用 | **炸**：`ReferenceError: _x is not defined` |
| 体内**没有**闭包 | 正常（IDE 不抽函数，`var` 留在原作用域） |
| 有闭包，但 `var` 提到 `for` 之前 | 正常 |
| 体内无 `var` | 正常 |

⇒ 修仙产物里 15 处「for-of 体内有 `var`」，**恰好只有 4 处**同时满足这两条（`_s$journey11/12`、`35/36`、`46/47`、`57/58`），也只有这 4 处真的炸。
⇒ 官方 `subpkg/logic/engine.logic.js` 里那 1 处**不满足**（体内没有闭包引用循环变量）⇒ 官方人生**不受影响**，一个字都不用动。

### 14.4 修法（改在降级器，不改产物、不改上游）

**为什么改降级器**：`runtime/engine.js` 是**生成物**（`scripts/build-xianxia-mp.mjs` 产出），
手改它下次构建就被覆盖、而且「规则 = 上游那份」就不成立了。
而这个坑的**来源就是降级这一步** ⇒ 在降级器里根治最合适：
上游源码不用动、产物不用手改、以后上游再出同样的写法也不会复发。

**做法**（`scripts/lib/es2015-downlevel.mjs`）：

- 新增 `fixForOfVarScope(code)`：把 for-of 循环体**最前面**那条 `var` 声明里
  **「循环头部用到过」**的那些变量，**提到 `for` 语句之前**（同一函数作用域）。
  语义完全等价（`var` 本来就是函数级提升），但转译后这条声明就留在循环体**外面**。
- 新增 `scanForOfVarScope(code)`：**AST 口径**的检测器（见 14.5）。
- `downlevelEs2020()` 在 babel 降级**之后**调用 `fixForOfVarScope`。

**两个必须处理的边界（开发时真踩到过）**：

| 边界 | 问题 | 处理 |
|---|---|---|
| `if (s) for (…) {…}`（for 不是语句列表里的独立语句） | 直接插 `var` 会变成 `if (s) var _x;` ⇒ **条件分支语义被改变** | 把整个 for **包进一个块**：`if (s) { var _x; for (…) {…} }`（`var` 仍是函数级提升 ⇒ 语义等价） |
| 纯文本切片的 **off-by-one** | 开发时把 `g(t)` 改成了 `v(t)`（包块时多算了一个花括号） | 函数内置**两道自检**：① 改完必须还能被解析；② **标识符集合必须完全一致**（多了少了都报错）。实测：故意把偏移改错 ⇒ 自检立刻报「丢了 g；多了 v」 |

**验证**（都是实测，不是推理）：

| 实验 | 结果 |
|---|---|
| 只把 4 处 `var` 提到 `for` 前 | IDE 里 `validateRun` 通过 |
| 只把那一处改写成不产生临时变量的等价写法 | 同样通过 |
| 4 处一起修 | 50 个随机种子 `validateRun` 全过；**真实出生页在 IDE 模拟器里转盘转出「林啸」、零未捕获异常** |

### 14.5 门禁同步（这类坑必须有门禁，否则会再溜到真机）

| 门禁 | 加了什么 |
|---|---|
| `xianxiabuild` | 新增一节「for-of 的 var 作用域」：用 `scanForOfVarScope` **直接扫产物**，出现即红 |
| `mpsyntax` | 新增 ②bis：扫**小程序端全部 js**（不只是修仙产物）⇒ 将来任何分包引入同类问题都会被拦下 |

**扫描口径**（四个条件同时成立才算命中，缺一不可，否则会误报）：
① 是 for-of / for-in 且循环体是 block；② 循环体第一条语句是 `var` 声明；
③ 循环**头部**用到了 ② 里的变量名；④ 循环体里有**闭包引用了循环变量**。

**反向验证（改坏必红）**：

| 注入的坏形态 | 期望 | 实测 |
|---|---|---|
| 有闭包引用 `t` + `var` 在体内 + 头部引用 | 命中 | **命中 1** ✓ |
| 有闭包但没引用 `t` | 不命中 | 0 ✓ |
| 无闭包 | 不命中 | 0 ✓ |
| 有闭包 + `var` 已提前 | 不命中 | 0 ✓ |
| 体内无 `var` | 不命中 | 0 ✓ |
| 头部不引用该 `var` | 不命中 | 0 ✓ |
| **整份修复前的旧产物** | 命中 4 处 | **精确命中那 4 处** ✓ |
| 把旧产物塞回仓库跑 `mpsyntax` | 报红 + 退出码 1 | **红 + exit 1** ✓ |
| 把旧产物塞回仓库跑 `xianxiabuild` | 报红 | **红** ✓ |

### 14.6 这一轮的教训（跨项目的通用价值）

- **「Node 里跑得通」不等于「微信里跑得通」**：`var` 的函数级提升在 Node 救了场，
  而微信的转译会改变作用域边界。⇒ 凡是小程序端的产物，**光靠 Node 门禁不够**，
  必须有一道**扫产物形态**的门禁。
- **这类 bug 的特征是「只在真机/IDE 炸、模拟器有时也炸、Node 全绿」** ⇒
  定位时要直接去 IDE 的**编译缓存**里看转译后的产物（`WeappCompileCache`），
  那是唯一能一眼看出「作用域被切断」的地方。
- **最小复现要按 IDE 的真实设置来**（`es6/enhance/minified/useCompilerModule`），
  否则会得到「探针全过 ⇒ 不是这个原因」的错误结论。

### 15.2 快照怎么接进来的（连不上 git 协议时也能接）

这台机器上 `github.com` 的 **git 协议连不上**（只有 `api.github.com` 与 `codeload` 通），
所以不能 `git fetch` 上游分支。处理办法：

1. 用 `gh api repos/buuzzy/xianxia-life/tarball/feature/adventure-preview-v01` 取源码包；
2. 在本地建成镜像目录（`git init` + 提交，工作树干净）；
3. **用 GitHub API 取上游的真实 `tree` sha**，与镜像 `git write-tree` 的结果**逐位比对**：
   本地 `c780c6c425f0dda82a09d7a6a0d3bfa6b4878e06` == 上游 `c780c6c425f0dda82a09d7a6a0d3bfa6b4878e06`
   ⇒ **镜像内容与上游那个 commit 逐字节相同**；
4. 刷新快照时**显式声明**上游提交与 tree：

   ```sh
   node scripts/build-xianxia-mp.mjs --refresh=/tmp/xl12-mirror \
     --upstream-commit=b519ac066a3499e0aced0fd9b5bd15ae855c3c49 \
     --upstream-tree=c780c6c425f0dda82a09d7a6a0d3bfa6b4878e06 \
     --upstream-branch=feature/adventure-preview-v01
   ```

   脚本会**核对镜像的 tree 与声明的 tree 是否一致**，不一致直接停 ——
   免得锁进去一个说不清的状态。

> 新增参数：`--upstream-commit` / `--upstream-tree` / `--upstream-branch`。
> 不给它们时行为不变（从本地 checkout 的 git 里读）。
