## 1. 十分钟版

### 1.1 事情是什么

《归山记》是一款修仙题材的**人生模拟文字游戏**：玩家活一生，做几十次抉择，走一条修仙（或不修仙）的路，结局由选择塑造。有网页端和微信小程序端两套界面。

2026-11-08 前后，你（产品方）连续四轮提出问题，我（开发方）逐轮做了实跑分析。四轮的问题依次是：

1. 「不评价剧情质量，分析一下我们的剧情框架。」
2. 「我想把剧情推倒重来……这是我最初关于剧情的想法，目前实现了吗？」
3. 「①前期会经历大量决策卡，呈现短期密集状态，且决策剧情相互之间没有关联；②这些决策以及非决策的人生经历的描述过于精炼、信息量密集……导致用户无法像看修仙小说那样『无脑』……真正需要用户决策的是『测灵根』这个环节……另外，我根据 1in8b 的决策设计写了一份报告请你阅读、分析。」
4. 「1in8b 最多活到 90-100 岁就结束寿命了，而且 1in8b 的 1x 非常慢……而我们是随着等级突破不断地增加寿元，倍速进程非常快……这让决策卡的触发间隔非常快，即便是一年。」

分析之后，双方就 **13 件待决事项**逐条达成一致（你全部采纳了我的推荐），并追加了**转向微信小程序、清理网页版**的新指令。

### 1.2 三条核心结论

| # | 结论 | 一句话 |
| --- | --- | --- |
| 1 | **原始设计实现了一半，且实现的部分与设想不同** | 轮盘没有背景故事线（出身是哈希随机的）；背景不收束（同一背景能发散成 5 条路）；测灵根→部门→心法三环断裂（**没有「部门」这一环**）；树枝尾端不接新树干；「与修仙无缘」不是结束游戏，而是 50 张卡的完整凡人一生。 |
| 2 | **框架是「内容已就位、调度未就位」** | 312 张卡里 84% 被豁免名单放行；实跑 86% 的提问绕过所有闸；一条命 45 张卡里只有 3–5 张是长线骨架，其余漂浮；7 条长线无桥、2 条整线零触达。 |
| 3 | **阅读体验的根因是「一年太短」，不是「卡太多」** | 每命决策卡 45 张（官方 56 张，同一量级）；但**「一年」只值 8 秒**（官方 43–67 秒）⇒ 一年里塞不下旁白 ⇒ **叙述:决策 = 1.29 : 1**（官方 6.5 : 1）。铺垫不是没写，是**写了也没地方放**。 |

## 2. 你的原始想法（浓缩，未失真）

这一节是**所有后续改动的准绳**，任何实现与它冲突都要回来找你确认。

| 轮次 | 你的核心主张 |
| --- | --- |
| 一 | 角色要有**理由去修仙**；理由在**轮盘时**设定（父母生病 / 救人一命 / 捡到法宝 / 生在宗门 / 名门望族 / 修仙世家…）。背景线索**只指向唯一结果**：一类指向「与修仙无缘，**结束游戏**」，一类指向「入宗门」。树形结构：**树干 → 树枝 → 树枝尾端进入新树干 → 重新走向别的树枝**。宗门内递进：**入宗门 → 测灵根 → 所属宗门部门 → 心法和功法选定 → 炼气期弟子修炼 → 炼气突破**。 |
| 二 | 当前「凡身到炼气」**散乱、没有主线牵引**。要评估剧情框架是否实现了最初的设计。 |
| 三 | ① 前期**大量决策卡**（测灵根、学医、渡口、宗门冲突），**短期密集**且**相互之间没有关联**；② 决策与非决策经历的描述**过于精炼、信息量密集** ⇒ 玩家**无法像看修仙小说那样「无脑」**，要投入大量阅读理解，还可能读不懂要点。**构思**：剧情背景从**非决策的人生经历**逐步呈现；真正要决策的只有「测灵根」这个环节本身，前面的铺垫（听到哪里招弟子、去玩/劳作、仙师招手、念念有词、点额头、瞬间大量信息涌入）放进人生经历；采药草试炼做成**强制性的**（宗门要求），决策集中在**救人的心理搏斗（救/逃/偷/躲）**和**与怪物/人的比拼（有概率死亡）**，其余非重大决策做成非决策经历。 |
| 四 | 1in8b **最多活 90–100 岁**就结束；1in8b 的 **1x 非常慢**，玩家能感受时间慢速或快速流程。我们**随境界突破不断增加寿元**，**倍速进程非常快**，**有些年岁阶段的时间流逝控制得一般**，导致**决策卡触发间隔非常快，即便是一年**。 |

**另外两条长期有效的授权**：
- 你有删除冗余剧情的权力，可基于修仙小说重构；不需要那么多故事线。
- **「选择塑造人」是主旨**；「与修仙无缘」那条线先简写、后续再扩展；轮盘 = 开局定好故事线（**不在前端展示**），玩家体验是「随机故事」。

## 4. 结论详述

### 4.1 框架：「内容已就位、调度未就位」

| 实测 | 数字 |
| --- | --- |
| 事件表总卡数 | 312 张 |
| 有结构的长线阶段卡 + 接头卡 | 48 + 27 = 75 张（24%） |
| 豁免名单覆盖 | 262/312 = **84%** |
| 实跑 40 条命 1613 次提问 | **1385 次（86%）绕过所有闸** |
| 一条命 41–50 次决策 | 只有 3 条长线是骨架，其余 38 张漂浮 |
| 60 条命触达 | 176/312 = 56.4% |
| 零触达族 | `beast` 0%（17 张）、`parcel` 0%（16 张） |
| 16 条长线触发极不均 | `sect_repair` 26/60 … `beast_eclipse` 0/60 |
| 长线有没有桥 | 9 条有桥、**7 条没桥** |
| 经典线 `content/nodes.js` 45 张 | 实测 40 条命**一张未发** |
| 结局 | 25 个，但 60 条命只出现 8 个 |
| 表达域修仙线覆盖 | 312/312 = 100%（入口是 `content/expressions/events/index.js` 的 `EVENT_ROWS`） |

**三处结构偏差**：豁免名单过宽（84%）、结构未暴露给玩家、7 条长线无桥 + 2 条整线零触达。

### 4.2 原始设计逐环核对

**已实现（5 项）**：
- 轮盘（`packages/adventure/birth.js` + `apps/preview/app.js:97-105`）—— 但只转姓名/地点/家庭；
- 「与修仙无缘」线（`content/mundane-stories.js` 50 张 `m11_*`）；
- 测灵根→入宗门收束（`reception` → `root_result`）；
- 16 条长线 = 树枝（`content/cultivation-stories.js` 的 `ROAD_CHAINS`）；
- 接头卡 = 接缝（`content/cultivation-joints.js` 的 `JOINT_NEXT_BEAT`）。

**未实现（5 项）**：
1. 轮盘无背景故事线（`packages/adventure/cultivation.js:28` 哈希随机，ordinary 70% 无故事）；
2. 背景不指向唯一结果（`reception` 3 选 + `root_result` 5 选 ⇒ 可发散 5 条路）；
3. 测灵根→部门→心法三环断裂（**无「部门」环**；`first_method` 选重心非心法；`network_method` 自动发）；
4. 树枝尾端不接新树干（`JOINT_NEXT_BEAT` 写死，7 条长线无桥）；
5. 「与修仙无缘」不是结束游戏。

### 4.3 阅读体验：「前期密集」成立，「信息量密集」换个说法也成立

1. **「前期密集」✅ 成立，但形态是「脉冲」**：12 个月窗口中位 0 张、87.2% 空白；0–26 岁 36 个月窗口 P90=4、最大 6；逐年 16 岁 1.27、**17 岁 2.18**、18 岁 0.93；一生 45 张里 4.38 张挤在 16–18 三年；官方 96% 的年份都有事（年均 1.242 张）。
2. **「信息量密集」⚠ 方向对，根因是设定塞在决策卡**：决策卡正文 **3.40 专名/百字** vs 旁白 **1.29**；每命决策卡中位 45（官方 56，同量级）、旁白中位 57 ⇒ **叙述:决策 = 1.29 : 1**（官方 6.5 : 1）；旁白间隔中位 39 个月；旁白池约 140 条且全是「事后交代」，**一条「当时正在发生」的场景铺垫都没有**；测灵根现为 **4 张卡 13 选项**（reception 3 → root_result 5 → first_method 3 → network_method 2）。

### 4.4 时间刻度（这条被复核修正过两次，见 §8.2）

- **官方**：`yearSec = clamp(paceMin*60/max(e0,60), 12, 120)`，paceMin=60 ⇒ 1 年 = 43–67 秒；UI 显示「1 年 ≈ X 秒」；`SPEEDS=[1,2,4,8,12,16]` + 快进。
- **我们**：`packages/adventure/progression.js:153` ⇒ 普通月份 1 年 = 8 秒；倍速网页端只有 `[1,2,4]`。
- **一生**：309 岁（中位，P90 364，最大 387）≈ **12.8 分钟（1x）**；官方 85 岁 ≈ 61 分钟。
- **时间账单**：**151+ 占一生 63% 时间只有 27% 内容**；真正在玩的 17–40 岁只占 6% 时间。
- **凡人与修士的寿元表**（`content/realms.js`）：凡身 88 / 炼气 120 / 筑基 210 / 金丹 350 / **元婴 560**。

### 阶段 1 · 年速（只动播放层，不动规则）

**公式**

```
1 年 = clamp(K ÷ 境界基础寿元, floor, 120) 秒
  童年（0–6 岁）：固定 8 秒/年（童年没决策也没内容，别拖）
  95 岁及以后：再封顶 lateCap 秒/年（元婴期 227 年只有 12 张卡，画面不能空着）
  长途行动期间（闭关/远行/渡劫准备）：保持现状（一年 1–5 秒）—— 那是「闭关跳过」的设计语义
```

**推荐参数**：`K = 5400`、`floor = 4`、童年 `8` 秒/年、`lateCap = 3` 秒、`LATE_FROM_AGE = 95`

| 参数组合 | 一生时长 | 对官方 61 分 | 相邻卡间隔（16-26 / 27-40 / 41-94 / 95+） |
| --- | --- | --- | --- |
| **现状** | 12.8 分 | 21% | 8 / 8 / 16 / 15 秒 |
| K=4800, late=3 | 38.5 分 | 63% | 16 / 21 / 43 / 45 秒 |
| **K=5400, late=3（推荐）** | **40.9 分** | **67%** | **16 / 23 / 46 / 45 秒** |
| K=5400, late=4 | 44.5 分 | 73% | 16 / 23 / 46 / 60 秒 |
| K=6000, late=4 | 46.8 分 | 77% | 16 / 25 / 49 / 60 秒 |

K 是**单一常数**，4800–6000 之间都合理；先按 5400 实现，看实际手感再定。

⚠ 与《待决事项》页面写的「K 留 4200/4800 两档」不一致 —— 那是**加童年特例之前**的校准。**以 5400 为准。**

**改动点 A · `packages/adventure/progression.js`（核心）**

```js
// 新增 import（content/realms.js 无任何 import ⇒ 不会成环；由 scripts/test-xianxia-cycle.mjs 验）
import {REALMS} from '../../content/realms.js';

// 新增常量（放文件顶部常量区，逐个写清来历）
const YEAR_SECONDS_K = 5400;      // 一年的秒数 = K ÷ 境界基础寿元
const YEAR_SECONDS_MIN = 4;       // 秒/年 下限
const YEAR_SECONDS_MAX = 120;     // 秒/年 上限（与官方同档）
const CHILDHOOD_AGE = 6;          // 童年分界
const CHILDHOOD_SECONDS = 8;      // 童年：一年 8 秒（与现状同）
const LATE_FROM_AGE = 95;         // 后期起点
const LATE_MAX_SECONDS = 3;       // 95 岁后一年封顶几秒

export function playbackSeconds(s){
  const j = longAction(s);
  if (j) return Math.max(10, Math.min(18, j.months/24)) / j.months;   // 长途分支不动
  if (age(s) < CHILDHOOD_AGE) return CHILDHOOD_SECONDS / 12;
  const cap = REALMS[s.player.realm]?.lifespan || 88;
  let sec = Math.min(YEAR_SECONDS_MAX, Math.max(YEAR_SECONDS_MIN, YEAR_SECONDS_K / cap));
  if (age(s) >= LATE_FROM_AGE) sec = Math.min(sec, LATE_MAX_SECONDS);
  return sec / 12;
}
```

### 7.3 踩过的坑（别再踩）

**代码层**
- 小程序产物非原生 ESM，bundle 的 `require` 在模块加载中返回半成品 ⇒ 任何「加载时读对方顶层常量」的环都白屏 ⇒ 靠 `xianxiacycle` 门禁守住；环检测要同时认 `import` 和 `export … from`。
- `scripts/check.mjs` 的导入检查器是纯正则 ⇒ 注释/字符串里的 `from './x.js'` 会误报。
- `scripts/verify-event-sequence.mjs --help` 会直接重写基线。
- 差异审查用字符串补丁还原会过期 ⇒ 用 HEAD 的 git worktree。
- ES 模块缓存 ⇒ 前后对照必须两个独立进程。
- **`playCultivation` 默认 `rulesVersion=11`**。
- `pick()` 会消耗 `random(s,'daily')` ⇒ 改 `automaticStory` 返回路径会改变随机流。
- 小程序端禁 `?.` / `??`；禁 ES2018 正则特性；禁 `wx.request`。
- `content/cultivation-stories.js` ↔ `content/mundane-stories.js` 互相 import ⇒ 提前触发 stories.js 会让 `card` 撞 TDZ。
- WXML 的 `{{}}` **不支持字符串拼接**（`+` 是算术 ⇒ `NaN`）⇒ 整句在 JS 侧拼好。
- 选项按钮的直接子元素 ≤ 3（官方 `.dec .ch button` 是两列 grid，第一列只有 1.6em 宽，第 4 个直接子元素会掉进窄列被压成竖排）。
- 顶栏**不许**给微信胶囊让位（不许出现 `padding-right` / `topPadRight`）；弹层顶部让位只用 `sheetPadTop()`。
- canvas 上的字体必须与 `app.wxss` 的变量同源（canvas 读不到 CSS 变量 ⇒ 字体族只能写死，但必须与 `--f-body` / `--f-mono` 逐字同源）。
- 视觉只用官方那套类名（`.topbar` / `.agebox` / `.speed .sps .sps-b` / `.panel` / `.dec` / `.ch` / `.cert` / `.roller` / `.shf` / `.idcard` …），**不许自造 `x-xxx` 视觉类**。

**工具链**
- 微信 CLI 出码三坑：先 `pkill -9 -f wechatwebdevtools`；二维码路径必须在 `os.tmpdir()` 且先建空文件；IDE 已开着时先 `cli close` → `cli open --port 9420` → `cli preview`。
- **浏览器 FilePanel**：`open_tab` 新标签会让旧页 `document.hidden===true` ⇒ 时间停走 ⇒ 点播放键恢复；两个标签页写同一 localStorage 键会互相关停 ⇒ 换端口；`navigate` 遇已有标签页报 `current_tab_occupied` ⇒ 用 `open_tab` 或 `reload`；`scroll` 的 `distance` 必须是 number。
- **HTML/JS**：`forEach(function(s){...})` 的参数会遮蔽外层同名累加器字符串 ⇒ 静默丢输出并抛 `Cannot read properties of undefined (reading 'toFixed')`；SVG 用 `innerHTML` 在容器 div 上生成比直接改 `<svg>.innerHTML` 更稳。
- **图表数据**：手算柱高/横轴刻度必错 ⇒ 一律用 JS 从数据数组生成图。
- `scripts/serve.mjs` 不放行 `/artifacts/` ⇒ 本地预览 artifacts 要另起 `python3 -m http.server`。
- **浏览器临时档案必须放 `os.tmpdir()` 且跑完就删**（放仓库里会让微信开发者工具编译崩溃）。

**分析层（本次新增，最容易再踩）**
- **时间刻度不能手算分段**：`playbackSeconds` 的长途分支（一年 1–5 秒）手算会漏 ⇒ 算出「一生 57 分」而实测是 **12.8 分**（差 4.5 倍）。**必须逐月采样。**
- **一个正确的数字可能挂在错误的解释下面**：「一生 12.5 分钟」这个数**是对的**，错的是把它归因成「一年只有 8 秒」—— 真相是「闭关期间一年 1 秒」+「普通月份一年 8 秒」两件事叠加。**每个结论的归因都要单独复核。**
- **改播放速度前先查有几条分支在决定它** ⇒ 只改主分支，效果会打折到只剩一半。
- **统计数组时先确认它是数组还是对象** ⇒ 用 `Object.keys()` 取数组会拿到下标，会把「命最多同时拿到 9 件」误报成「只碰到 9 种道具」（实测 18/43 被误报成 9/43）。
- **浏览器 ↔ Node 做逐值全等比对时，排序不许用 `localeCompare`** ⇒ 走 ICU 区域规则，中文在浏览器与 Node 排序不同 ⇒ 改用逐字比较（`<` / `>` 比 UTF-16 码元），优先用 ASCII 的 id 做次级键。
- **门禁断言「不许出现某字符串」要区分「真依赖」与「文案提及」** ⇒ 判定口径要落到动作上（`readFileSync` / `import()` / `path.join` / `from '…'`），文案必须留。
- **用脚本做大段文本替换时锚点必须唯一**，改完必须验证没丢内容（`edit` 工具找不到会报错，比脚本安全）。
