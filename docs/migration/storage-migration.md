# 玩家存档迁移协议（设计 · 尚未实现）

> 状态：**未实现**。本文件是协议设计，供实现时照着做。
> 迁移方案 §6 是原始依据，本文件把它落成字段级规格。

## 为什么必须单独做

微信本地缓存按小程序身份隔离。新产品即使用**相同的键名**（`xianxia.v1.*`），
也**读不到**原 1in8b AppID 下的缓存 ⇒ 必须有「旧端导出 → 新端导入」这条通路。

现有存档层（`miniprogram/subpkg/xianxia/bridge/storage.js`）有分片、双 manifest 槽与写后校验，
但公开接口只有保存 / 读取 / 列出 / 删除，**没有面向玩家的导出与导入**。

## 传输方式

首选**玩家自行保存与传送的 JSON 文件**：

- 旧小程序：选定一段或多段归山记人生 ⇒ 生成一个迁移文件。
- 新小程序：选择文件 ⇒ 核验 ⇒ 导入。

具体用哪套微信文件 API（保存到聊天 / 选文件）**先在开发者工具与真机上验证**再定稿。
若文件通道不满足真机条件，另设计文本通道；**大存档不塞二维码、不要求玩家手工拼接几十段文字**。

**不引入**服务器、中转账号或云同步作为前提。文件由玩家自己传送。

## 封套字段

| 字段 | 用途 | 约束 |
| --- | --- | --- |
| `format` | 区别归山记迁移文件与官方人生 / 普通 JSON | 固定值，如 `guishanji.migration` |
| `formatVersion` | 封套版本 | 整数，递增 |
| `sourceProduct` | 来源产品标识 | 如 `1in8b-xianxia` / `guishanji` |
| `sourceBuild` | 来源构建版本 | 规则版本 + 产物哈希 |
| `createdAt` | 导出时间 | ISO 字符串 |
| `activeId` | 继续哪段人生 | 必须存在于人生列表内 |
| `lives[]` | 每段人生 | 完整状态 + 规则版本 + 字节数 |
| `checksum` | 内容校验摘要 | 查截断/传输损坏；**普通摘要，不是防篡改认证** |

每段人生内部必须保留：年月、随机流状态、出生、人物、库存、待选项、长行动。

## 导入规则

1. 写入**之前**核验：格式、文件大小、字段、受支持的规则版本、状态完整性。
2. **规则 8 保持 8，规则 12 保持 12**；不重新生成种子、命盘、寿元、随机数或往事。
3. 重复 ID：内容完全相同 ⇒ 提示已存在；内容不同 ⇒ 让用户选择另存，**不静默覆盖**。
4. 确认用户选择与容量后，走**原有分片 / 双槽写入协议**逐段保存并读回校验；
   最后明确列出「成功 / 未导入 / 失败」的人生。
5. 多人生文件若部分导入，界面**必须说明**，不假称整包成功；
   尚未验证的新 manifest 不能取代可读的旧 manifest。
6. 导出后**不自动删除**原 AppID 的数据；导入后也**不要求**玩家立即卸载旧小程序。

## 必须做的验证

- 从原 1in8b AppID 实际导出一个规则 8 存档、一个规则 12 存档，
  在新 AppID 下导入后能继续。
- 模拟截断 / 格式错误 / 不支持规则 / 额度不足 / 写入异常 / 应用中断，
  验证**旧档仍可继续**。
- 官方 `one8b.*` / `o8b.*` 存档逐字不变。

## 网页旧档

- 若保留原网页域名与存储来源，尽量维持网页存档键与协议。
- 换域名 / 协议 / 端口会改变浏览器存储来源 ⇒ **不能承诺**旧存档自动出现在新站点。
- HTML 存档与微信分片档的存储协议不同：**共享的是合法人生状态**，
  不是把 localStorage 直接复制进 `wx` 缓存。
